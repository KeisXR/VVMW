# lrcserve 動画ID endpoint 実装仕様

最終更新: 2026-11-23

`lrcserve` (`https://k3isd.net/lrc`) に追加する、YouTube動画IDから歌詞を返すendpointの仕様。全体像は [lrclib-integration-status.md](lrclib-integration-status.md) を参照。

Unity側 (`Runtime/VVMW/Core_LRCLIB.cs`) は実装済みで、C#とUdonSharpのコンパイルは通っている。VRChat上での実機確認はまだ行っていない。この仕様はそのコードの挙動に合わせて書いてある。

サーバー側は2026-11-23に実装され、8章のうち `curl` で確かめられる項目は確認済み。未確認なのは「別のIPからの先回り応答」と「歌詞受信後の報告の記録」の2つ。

## 1. 背景

VRChatのUdonは、実行時にURLを組み立ててアクセスすることができない。アクセスできるのは、ワールドのビルド時に埋め込んだ固定URLだけである。

そのため、ユーザーがURL欄に直接貼ったYouTube動画について、clientは「この動画の歌詞をください」と1回のリクエストで伝えられない。代わりに、動画ID (11文字) を2文字ずつに分け、「その2文字に対応する固定URL」へ順番にアクセスすることでIDを伝える。サーバーは届いた断片を繋ぎ合わせて動画IDを復元する。

## 2. 追加するendpoint

| Method | Path | 用途 |
|---|---|---|
| GET | `/lrc/yt/{pool}/id/{chunk}/{chars}` | 動画IDの断片を受け取り、歌詞が分かれば返す |
| GET | `/lrc/yt/{pool}/report` | 「この歌詞は違う」の報告 |

どちらもGETのみ。VRChatからはヘッダーやbodyを付けられないので、情報はすべてパスに入っている。

### パスの各部分

| 部分 | 内容 |
|---|---|
| `{pool}` | ワールドごとの識別子。Unity側で `a-z` `0-9` `_` `.` `-` のみに正規化される。例: `myworld` |
| `{chunk}` | 断片の位置。`0`〜`5` |
| `{chars}` | 断片の中身。`chunk` が `0`〜`4` のときは2文字、`5` のときは1文字 |

`{chars}` に使われる文字は次の64種類。**大文字と小文字は別の文字**なので、パスを小文字化してはいけない。

```text
ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789-_
```

断片と動画IDの対応:

| chunk | 動画IDの何文字目か (1始まり) |
|---|---|
| 0 | 1〜2文字目 |
| 1 | 3〜4文字目 |
| 2 | 5〜6文字目 |
| 3 | 7〜8文字目 |
| 4 | 9〜10文字目 |
| 5 | 11文字目 |

動画ID `dQw4w9WgXcQ` の場合、clientは次の順でアクセスする。

```text
GET /lrc/yt/myworld/id/0/dQ
GET /lrc/yt/myworld/id/1/w4
GET /lrc/yt/myworld/id/2/w9
GET /lrc/yt/myworld/id/3/Wg
GET /lrc/yt/myworld/id/4/Xc
GET /lrc/yt/myworld/id/5/Q
```

範囲外の `chunk`、長さの合わない `{chars}`、64種類以外の文字を含むリクエストは400で拒否してよい (正規のclientからは届かない)。

## 3. clientの挙動

サーバーの設計に関わる部分だけを書く。

- chunk 0から順に、**1本ずつ応答を待ってから**次を送る。同じclientから断片が同時に届くことは基本的にない。
- VRChatの制限で、文字列の取得は**ワールド全体で5秒に1本**。断片の間隔は最短5秒で、動画タイトル取得など他の取得と重なるとさらに空く。6本送りきるのに30秒以上かかることがある。
- 応答JSONの `videoId` が自分の動画IDと**完全一致**したら、その応答を歌詞として採用し、残りの断片は送らない。
- 一致しなければ次の断片へ進む。chunk 5まで送っても一致しなければ、**1回だけ**chunk 0からやり直す。それでも一致しなければ「歌詞なし」と表示して止まる。
- **404は「まだ答えられない」として扱い、次の断片へ進む。** 404以外のエラー (5xx、タイムアウト、接続失敗など) は取得失敗として扱い、そこで送信を止める。その後、キューの更新など再生状況の同期をきっかけに、同じ動画のchunk 0から送り直すことがある。
- 動画が切り替わると、送信途中でも新しい動画のchunk 0から始める。
- 同じinstanceにいる全員が、それぞれ自分で断片を送る。10人いれば、未知の動画1本につき最大60本届く。

## 4. `/yt/{pool}/id/{chunk}/{chars}` の処理

### 4.1 保持する状態

**(a) 送信途中の断片**

- キー: 接続元IP + `{pool}`
- 値: 位置ごとの `{chars}` (最大6個) と、最後に断片を受け取った時刻
- 有効期限: 最後の断片から90秒 (推奨値)。期限切れは破棄する。

接続元IPは、手前のproxyが付けたヘッダーから取る。nginxのIPで束ねてしまうと全員の断片が混ざる。

`k3isd.net` はCloudflare経由なので、`CF-Connecting-IP` を使う。`X-Forwarded-For` の先頭の値は送信者が自由に書けるため、そのまま信用してはいけない。

実装は `CF-Connecting-IP` → `X-Real-IP` → 接続元アドレスの順に見ており、`X-Forwarded-For` は参照しない。偽の `X-Forwarded-For` / `X-Real-IP` を付けても同じclientとして扱われ、流量制限も回避できないことを2026-11-23に `curl` で確認した。偽の `CF-Connecting-IP` はCloudflareが403で拒否する。Cloudflareを通さずoriginへ直接届く経路がある場合は、nginxで `X-Real-IP` を上書きしておくこと (この経路は未確認)。

**(b) 解決済みの動画**

- キー: 動画ID
- 値: 歌詞の検索結果 (歌詞なしも含む) と、どの `{pool}` でいつ解決したか
- 用途: 6個揃う前に答える「先回り応答」(4.3) と、同じ動画の再検索を避けるため。
- 保持期間と件数は任意。pool ごとに直近200件・24時間程度あれば、同じinstanceの2人目以降には十分効く。

**(c) 最後に返した動画**

- キー: 接続元IP + `{pool}`
- 値: そのclientへ最後に返した `videoId` と、返した歌詞のLRCLIB id
- 用途: 報告 (5章)。

### 4.2 手順

リクエストごとに次を行う。

1. `chunk` が `0` なら、そのclientの (a) を破棄する。
2. (a) の該当位置に `{chars}` を書き込む。同じ位置にすでに値があれば上書きする。最終受信時刻を更新する。
3. 位置0〜5がすべて揃っていれば、順に繋げて11文字の動画IDにする。**揃った場合**は4.4へ。
4. 揃っていなければ、先回り応答 (4.3) を試す。答えられなければ4.5の「未解決」を返す。

### 4.3 先回り応答 (任意だが推奨)

6個揃っていなくても、心当たりのある動画があれば、その歌詞を先に返してよい。

1. (a) の位置0から連続して埋まっている部分を繋げ、動画IDの先頭部分 (prefix) とする。
2. (b) の中から、動画IDがそのprefixで始まるものを探す。同じ `{pool}` で解決したものを優先し、その中では新しい順に選ぶ。
3. 見つかれば (c) を更新し、その動画の歌詞を `videoId` 付きで返す (4.4と同じ形)。

clientは `videoId` が完全一致しない応答を捨てて次の断片へ進むので、**外れた候補を返しても誤表示にはならない**。当たれば、そのclientは残りの断片を送らずに済む。同じinstanceで誰かが先に解決していれば、他の人は1本目 (chunk 0) で歌詞が出る。

先回り応答では新たに検索を走らせず、(b) に保存済みの結果だけを返すこと。

### 4.4 6個揃った場合

1. 動画IDが `^[A-Za-z0-9_-]{11}$` に合うことを確認する。
2. (b) に結果があればそれを使う。なければ、`https://www.youtube.com/watch?v={videoId}` を対象に、既存の歌詞検索処理 (`/nomseek/{pool}/{slot}/lyrics` がslotの動画に対して行っているのと同じ処理) を実行し、結果を (b) に保存する。
3. (c) を更新する。
4. そのclientの (a) を破棄する。
5. 既存の歌詞レスポンスに `videoId` を加えたJSONを、200で返す。

**歌詞が見つからなかった場合も、動画が存在しなかった場合も、`videoId` を付けて200で返す。** こうするとclientは即座に「歌詞なし」と確定できる。ここで404や `videoId` なしの応答を返すと、clientは同じ6本をもう一度送り直してしまう。

存在しない動画IDは、(b) に入れても先回り応答の候補にはしないこと。届く順番が入れ替わって壊れたIDが組み上がることがあるため (7章)。

### 4.5 レスポンス

共通:

- `Content-Type: application/json; charset=utf-8`
- `Cache-Control: no-store` を付ける。同じURLへのアクセスでも、返す内容はそのときの状態で変わるため。
- リダイレクトは使わない。

**歌詞あり (200)**

```json
{
  "videoId": "dQw4w9WgXcQ",
  "id": 123456,
  "trackName": "Never Gonna Give You Up",
  "artistName": "Rick Astley",
  "plainLyrics": "We're no strangers to love\n...",
  "syncedLyrics": "[00:18.52] We're no strangers to love\n...",
  "instrumental": false
}
```

**動画は特定できたが歌詞なし (200)**

```json
{
  "videoId": "dQw4w9WgXcQ",
  "plainLyrics": "",
  "syncedLyrics": "",
  "instrumental": false
}
```

**未解決 (まだ断片が足りず、先回りもできない)**

次のどちらでもよい。clientはどちらも「次の断片を送る」として扱う。

- 200で `{}`
- 404 (bodyは任意)

各項目の扱い:

| 項目 | 型 | clientでの扱い |
|---|---|---|
| `videoId` | 文字列 | 自分の動画IDと完全一致したときだけ、この応答を採用する。**文字列で返すこと** |
| `id` | 数値または文字列 | LRCLIBのid。表示には使わない |
| `trackName` / `artistName` | 文字列 | 保持のみ |
| `syncedLyrics` | 文字列 | LRC形式。1行以上解釈できれば同期歌詞として表示する |
| `plainLyrics` | 文字列 | 同期歌詞が無いときに使う。現状のUIは「同期歌詞なし」と表示する |
| `instrumental` | 真偽値 | `true` なら「インストゥルメンタル」と表示する |

`videoId` 以外は、既存の `/nomseek/.../lyrics` と同じ形でよい。

## 5. `/yt/{pool}/report` の処理

clientで「歌詞が違う」ボタンが押されると、このURLに1回アクセスが来る。パスには動画の情報が無いので、(c) を使って対象を決める。

1. 接続元IP + `{pool}` で (c) を引く。
2. 見つかれば、その動画と、そのとき返したLRCLIB idの組に対する報告として、既存の `/nomseek/{pool}/{slot}/report` と同じ処理を行う。該当する (b) の結果は破棄し、次回は別の候補を検索させる。
3. 見つからなければ何もしない。

応答の内容とステータスは何でもよい。clientは成功でも失敗でも「報告を送信しました」と表示する。

報告のあと、clientは次に歌詞を読み直すとき、同じ動画のchunk 0からもう一度送ってくる。

## 6. 具体例

`pool` は `myworld`、動画IDは `dQw4w9WgXcQ` とする。

### 6.1 サーバーが初めて見る動画

| 順 | リクエスト | 応答 |
|---|---|---|
| 1 | `id/0/dQ` | `{}` |
| 2 | `id/1/w4` | `{}` |
| 3 | `id/2/w9` | `{}` |
| 4 | `id/3/Wg` | `{}` |
| 5 | `id/4/Xc` | `{}` |
| 6 | `id/5/Q` | 歌詞 (`videoId: "dQw4w9WgXcQ"`) |

clientは6本目の応答を採用する。所要時間は25〜30秒程度。

### 6.2 同じinstanceの別の人 (先回り応答あり)

6.1のあと、別のIPから:

| 順 | リクエスト | 応答 |
|---|---|---|
| 1 | `id/0/dQ` | 歌詞 (`videoId: "dQw4w9WgXcQ"`) |

`dQ` で始まる解決済みの動画があるので、1本目で返せる。clientはここで止まる。

### 6.3 先回りが外れた場合

`dQw4w9WgXcQ` が解決済みの状態で、別の動画 `dQabcdefghi` が再生されたとき:

| 順 | リクエスト | 応答 |
|---|---|---|
| 1 | `id/0/dQ` | 歌詞 (`videoId: "dQw4w9WgXcQ"`) ← clientは捨てる |
| 2 | `id/1/ab` | `{}` (prefix `dQab` に合う動画が無い) |
| 3〜5 | `id/2/cd` `id/3/ef` `id/4/gh` | `{}` |
| 6 | `id/5/i` | 歌詞 (`videoId: "dQabcdefghi"`) |

### 6.4 歌詞が無い動画

6本目で次を返す。clientは即座に「歌詞なし」と表示し、送り直さない。

```json
{"videoId": "dQw4w9WgXcQ", "plainLyrics": "", "syncedLyrics": "", "instrumental": false}
```

### 6.5 途中で動画が切り替わった場合

| 順 | リクエスト | サーバーの状態 |
|---|---|---|
| 1 | `id/0/dQ` | `{0: dQ}` |
| 2 | `id/1/w4` | `{0: dQ, 1: w4}` |
| 3 | `id/0/9b` | chunk 0なので破棄して `{0: 9b}` |
| 4 | `id/1/Zk` | `{0: 9b, 1: Zk}` |

## 7. 起こりうる乱れと対処

**届く順番の入れ替わり**

動画が切り替わる瞬間、VRChat側で前の動画の断片が1本だけ待ち行列に残り、新しい動画の断片より後に届くことがある。VRChatは待ち行列をランダムな順で処理するためである。

- 多くの場合、新しい動画の同じ位置の断片が後から届いて上書きされるので、問題にならない。
- まれに古い断片のほうが後に届き、壊れた動画IDが組み上がる。このときサーバーは壊れたIDで検索し、`videoId` に壊れたIDを入れて返すことになる。clientは一致しないので捨て、chunk 0からやり直す。

サーバー側で特別な対処は要らない。壊れたIDを先回り応答の候補にしないこと (4.4) だけ守ればよい。

**同じIPから別々の動画**

同じ回線の2人が、同じワールドの別々のinstanceで違う動画を同時に再生すると、(a) が混ざる。結果は上と同じで、clientの照合で弾かれてやり直しになる。同じinstanceなら全員が同じ動画を再生しているので、混ざっても同じIDになる。

**大量のリクエスト**

URLは公開されるので、VRChat以外からも叩ける。IPごとの流量制限と、(a) (b) (c) の件数上限を設けること。正規のclientは1 IPあたり5秒に1本を超えない。

## 8. 受け入れ確認

`curl` で確認できる項目。`$B` は `https://k3isd.net/lrc/yt/test` とする。

- [ ] `$B/id/0/dQ` → `$B/id/5/Q` を順に叩くと、6本目で `videoId` が `dQw4w9WgXcQ` のJSONが返る。
- [ ] その後、別のIPから `$B/id/0/dQ` を叩くと、1本目で同じ歌詞が返る。
- [ ] 途中まで送ってから `$B/id/0/..` を叩くと、溜めた断片が捨てられる (6.5)。
- [ ] 歌詞の無い動画で、6本目が `videoId` 付きの200になる。404や `{}` にならない。
- [ ] 存在しない動画IDで、6本目が `videoId` 付きの200になり、その後の先回り応答に出てこない。
- [ ] `$B/id/0/dq` と `$B/id/0/dQ` が別の断片として扱われる (大文字小文字の区別)。
- [ ] 断片を送って90秒以上空けてから続きを送ると、前の断片が使われない。
- [ ] 歌詞を受け取ったあと `$B/report` を叩くと、その動画とLRCLIB idへの報告として記録される。
- [ ] 何も受け取っていないIPから `$B/report` を叩いても、エラーにならず何も記録されない。
- [ ] 応答に `Cache-Control: no-store` が付いている。
- [ ] nginx越しでも、状態がclientごとのIPで分かれている。
- [ ] 偽の `X-Forwarded-For` を付けても、別のclientとして扱われず、流量制限も回避できない。

## 9. 未確認の事項

Unity側を実機で動かしていないため、次の点は確認できていない。安全側に倒した指定にしてある。

- VRChatが同じURLの応答をキャッシュするかどうか。念のため `Cache-Control: no-store` を指定している。
- VRChatの文字列取得のタイムアウト時間。6本目は検索が終わるまで応答を待たせることになるので、数秒以内に返すのが望ましい。検索が長引く場合は、いったん `{}` を返して検索を続け、clientのやり直し (chunk 0〜) の中で先回り応答として返す方法がある。
- リダイレクトを挟んだときの挙動。使わない前提にしている。
